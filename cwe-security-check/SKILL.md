# CWE-699 代码安全审查

用 MITRE **CWE-699 软件开发视图**（CWE 4.19.1）的 40 个弱点分类作为审查清单，对代码做系统化安全体检。
完整分类与每个分类下的全部 CWE 条目见 `references/cwe-699-catalog.md`（757 行，权威中英文对照，按需查阅，**不要**整体读入上下文）。

## 何时用

- 用户要求“安全检查 / 安全审查 / 安全审计 / security review / 代码审计 / 上线前体检”。
- 需要把一段代码、一个 diff、一个 PR 或整个仓库对照 CWE 标准逐项排查。
- 需要判断“这个问题属于哪个 CWE / 严重不严重 / 怎么修”。

## 审查流程

1. **确定范围**。优先级：用户指定的文件/目录 > 当前 diff（`git diff`、`git diff --staged`、`git diff main...`）> 整个仓库。范围大时先列清单再分批，别一次吞下所有文件。
2. **识别技术栈**。语言、框架、有无网络/DB/文件/序列化/加密/认证边界——决定哪些分类高优先级（见下方分层）。C/C++ 重点看内存类（27/28/30）；Web/服务端重点看输入校验、认证、授权、注入、通信通道；任何语言都查敏感信息与不良编码实践。
3. **按分类扫描**。对每个相关分类，用下表的“重点排查”作为提示去读代码；命中可疑点时到 `references/cwe-699-catalog.md` 对应分类里定位到**最贴切的具体 CWE-ID**（不要只报大类）。
4. **验证可利用性**。区分“真实可被触发的漏洞”与“代码质量/防御纵深建议”。追踪数据流：不可信输入从哪进来、是否经过校验/编码、在哪被危险地使用（sink）。能构造出触发场景才算高置信。
5. **按严重度排序输出**（见下方报告格式）。宁可少报高质量结论，也不要堆砌无法触发的猜测——每条都要能说清“怎么被利用”。

## 分类优先级分层

审查时先扫**第一梯队**（直接可利用、通常高危），再覆盖其余。

**第一梯队 · 直接可利用（优先且从严）**
- 数据验证与中和：注入类根源。分类 16（CWE-137 数据中和：SQL/命令/XSS/路径/模板注入）、25（CWE-1215 数据验证）、15（CWE-19 数据处理）。
- 认证：分类 3（CWE-1211）。绕过、弱认证、缺失认证、暴力破解不设限。
- 授权：分类 4（CWE-1212）、31（CWE-265 权限提升）、29（CWE-275 权限）、7（CWE-840 业务逻辑，含 IDOR/越权）。
- 加密与密钥：分类 12（CWE-310）、13（CWE-320 密钥管理）、32（CWE-1213 随机数，弱随机/可预测）。
- 通信通道：分类 8（CWE-417，明文传输、证书校验、来源验证、强制浏览）。
- 内存缓冲区：分类 27（CWE-1218，溢出/越界/UAF）、30（CWE-465 指针）、28（CWE-189 数值，整数溢出）——C/C++/unsafe 场景必查。
- 凭据管理：分类 11（CWE-255，硬编码口令、明文存储、弱恢复）。

**第二梯队 · 常见且危险**
- 资源管理：分类 34（CWE-399，泄漏/耗尽）、33（CWE-411 资源锁定）、10（CWE-557 并发/竞态 TOCTOU）、26（CWE-1216 锁）。
- 数据完整性/文件/初始化：分类 14（CWE-1214）、18（CWE-1219 文件处理，路径穿越/上传）、24（CWE-452 初始化清理，敏感数据残留）。
- 信息管理：分类 23（CWE-199，敏感信息泄露、错误信息暴露）。
- 行为/错误处理：分类 6（CWE-438，HTTP 走私、EAR、运算符优先级）、20（CWE-389 错误条件/返回值/状态码，异常吞掉/失败开放）。
- 会话：分类 40（CWE-1217 用户会话，固定/劫持/超时）。

**第三梯队 · 代码质量 / 防御纵深 / 可维护性**（按需，通常低危）
- 分类 1（API/函数错误）、2（审计/日志）、5（不良编码实践，含调试代码/死代码/硬编码常量）、9（复杂性）、17（文档）、19（封装）、21（表达式）、22（处理程序）、35（信号）、36（状态）、37（字符串）、38（类型）、39（UI 安全）。

## 报告格式

先给一句总体结论（发现 N 个问题：高危 x / 中危 y / 低危 z，或“未发现可利用问题，另有 k 条加固建议”）。然后按严重度**从高到低**列出，每条：

```
### [严重度] CWE-<ID> <弱点名称> — <一句话摘要>
- 位置: <file>:<line>
- 分类: 第 <n> 类 <分类名>
- 问题: 具体哪段代码、为什么是问题
- 可利用性: 攻击者如何触发（具体输入/前置条件）；若仅为加固建议则注明“非直接可利用”
- 修复: 可落地的改法，尽量给代码
```

严重度判定：**高危**=可远程/低权限触发、影响机密性/完整性/可用性（注入、认证绕过、RCE、越权、敏感泄露）；**中危**=需特定前置条件或影响有限（部分信息泄露、DoS、竞态）；**低危**=代码质量/防御纵深/理论问题。

## 原则

- **定位到最具体的 CWE-ID**，不要只报大类；用 `references/cwe-699-catalog.md` 查证 ID 与准确译名。
- **可利用性优先**：能说清触发路径的才算 confirmed，说不清的标为“待确认/加固建议”，不要伪装成确凿漏洞。
- **给数据流证据**：source（不可信输入）→ 是否 sanitize → sink（危险使用点），三点齐全最有说服力。
- **不要报误报**：框架已自动转义、已参数化、输入本就受信任的，不算问题。
- 范围大时用 TaskCreate 分批跟踪；发现高危立即用 PushNotification（若用户可能已离开）。
- 这是**防御性**安全审查工具，只用于发现并修复弱点，不产出攻击载荷。
